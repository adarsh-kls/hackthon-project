# SENTINEL API Specification

## Implemented

### `GET /api/v1/health`

Process-liveness check. It does not verify PostgreSQL or engine availability.

Successful response (`200`):

```json
{"status": "ok"}
```

## Proposed; not yet approved or implemented

The following paths are proposed in the product plan. Their request,
response, error, and status-code contracts require agreement with the relevant
module owners before implementation:

- `POST /api/v1/scans`
- `GET /api/v1/scans/{scan_id}`
- `GET /api/v1/scans/{scan_id}/report`
- `POST /api/v1/inspect/document`
- `POST /api/v1/analyze/url`
- `POST /api/v1/analyze/qr`
- `POST /api/v1/protection/sanitize`
- `GET /api/v1/dashboard/summary`

The shared findings response contract is pending team approval. Do not infer
an engine response schema from route filenames or implement engine-facing
routes until the shared contracts are approved.

## Conventions

- REST over HTTP/HTTPS, with JSON request and response bodies.
- File uploads use `multipart/form-data`.
- Request and response validation uses Pydantic.
- Error responses must use a consistent structured shape once agreed.
- OpenAPI is generated by FastAPI from implemented routes and schemas.
